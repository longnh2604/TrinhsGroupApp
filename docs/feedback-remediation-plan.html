2. Decisions needed from you before Sprint 1 starts

D1 — Google Sign-in on iOS drags Sign in with Apple in with it (App Store Guideline 4.8)

Apple requires that an app offering a third-party or social login also offer an equivalent privacy-preserving login. Shipping Google Sign-in alone on iOS is a rejection risk, and this app was already rejected once (2026-08-18), so the review margin is thin.

Recommendation: ship Sign in with Apple + Google Sign-in together on iOS. On Android, Google Sign-in alone is fine; Apple sign-in is not required there.

Alternative if you want a cheaper release: defer FB-3 entirely to a later version and ship Sprints 1 and 3 first. FB-3 is the single biggest item in this plan (~5.5 dev-days plus server work); dropping it halves the schedule.

D2 — Facebook Login: recommend declining

The report lists it as a "consider". It adds an SDK, a Meta app review, and a second privacy disclosure for a login method that overlaps Google almost entirely. Cheapest correct answer is Apple + Google, no Facebook. Say the word if you want it and it becomes a +2 dev-day item.

D3 — The report describes features this app does not have

FB-2 and FB-4 recommend showcasing "live tracking" and "table reservations". The app has neither: fulfilment is pickup date/time, and there is no reservation flow. Screenshots and the walkthrough must show what actually exists (menu browsing, add-ons, pickup slot, order status, vouchers/points) — inventing them would be false advertising and a store violation.

Confirm: we treat "live tracking" as the existing order-status progress card, and drop "table reservations" from all copy. No reservation feature will be built under this plan.

D4 — Content owner for FB-1, FB-4, FB-8

Store description keywords, screenshot design, and per-dish ingredient/allergen text are not engineering work; they are content that someone at Trinhs has to write and sign off. FB-8 in particular is blocked until the kitchen supplies ingredient and allergen text per dish — the app code is half a day, the content is the long pole. Nominate an owner and a date, or FB-8 slips out of this plan.

3. Approach per item, and what gets deliberately skipped

FB-2 — New-user walkthrough iOS 1.5d Android 1d

An onboarding carousel already exists in the tree and nothing navigates to it: TrinhsGroup/View/Onboard/OnboardingView.swift, OnboardCardView.swift, StartButtonView.swift, with slide data in App/Config.swift:15 and the ONBOARD_ENABLED flag at App/Config.swift:12. App/TrinhsGroupApp.swift goes splash → MainView and never touches it. The KMP side already has the matching shared/.../model/Onboard.kt.

  • Gate it on a first-launch flag in TrinhsGroupApp.swift (@AppStorage), shown once, with the existing skip/start button.
  • Rewrite the three slides to today's app: order pickup food, add-ons and options, vouchers and points. The current copy still says "Use discount code" and "bank transfer, payid", which the trinh-app/v1 migration retired.
  • Needs 3 slide images from design (existing onboard-1..3 assets are stale).

Skipped: interactive coach-mark tour overlaid on the live UI (tooltip framework, per-screen anchors, tour state machine). Add when onboarding funnel data shows drop-off the carousel does not fix.

Verify — fresh install shows the carousel once; skip works; relaunch goes straight to Home; existing users upgrading never see it.

FB-3 — Google + Apple sign-in WP 1.5d iOS 3d QA 1d Android 2d

Today login is email/password only (View/Authorization/LoginView.swift → AuthViewModel.onAuthUser → AuthServices → jwt-auth/v1/token). There is no social route on the server: wordpress-plugin/trinh-app-api.php registers /me, /me/orders, /me/orders/preview, cancel, history, payment-intent, /me/vouchers, /payment-methods, /products/{id}/addons and /register — nothing else.

  • Server (new): one route, POST /trinh-app/v1/auth/social. Takes provider (apple|google) plus the provider identity token. Verifies the token signature and audience against the provider's published keys server-side, matches or creates the WP customer by verified email, then returns the same JWT shape the app already consumes, so AuthViewModel keeps its existing success path.
  • Trust boundary — no shortcuts here: the identity token is verified on the server (issuer, audience/client id, expiry, signature). The app never sends an email or a user id the server trusts. Same rule the existing /me routes follow: identity comes from the token, never from client input.
  • iOS: Sign in with Apple via AuthenticationServices (no pod, needs the capability added to the target and the entitlement in the App ID) and Google via GoogleSignIn. Two buttons on LoginView and SignupView.
  • Account collision: a Google/Apple email that already has a password account links to that same WP user rather than creating a duplicate. Also handle Apple's private relay addresses and the fact that Apple returns the name only on first authorisation.

Skipped: Facebook (D2); Firebase Auth as a middle layer — the app already has its own JWT/Keychain path (Utility/KeychainStore.swift) and routing auth through Firebase would mean two identity systems for one login.

Verify — new Google user creates a WP customer and can place an order; the same email logging in by password lands on the same account with the same order history; Apple relay email works; token with a wrong audience is rejected with 401; declined Apple authorisation leaves the app in a clean state.

FB-5 — In-app feedback WP 0.5d iOS 0.5d Android 0.5d

This is nearly built already. wordpress-plugin/trinhs-feedback-wheel/ is a post-order 3-question survey with a signed-token link (Trinhs_FW_Token::sign, Trinhs_FW_Config::feedback_url) today delivered by email on order completion (includes/class-invite.php).

  • Server: add GET /trinh-app/v1/me/feedback-link — for the signed-in user, mint the same signed URL for their most recent eligible order (or return empty when none).
  • iOS: a row in ProfileView plus a CTA on the completed-order detail, opening the URL in SFSafariViewController.

Skipped: a native in-app survey UI, and a second free-text feedback channel. The wheel is the survey; duplicating it natively buys nothing and splits the responses across two stores.

Verify — user with a completed order sees the row, opens the wheel already identified, and the response lands in the existing WP admin table; user with no eligible order sees no row; the link rejects tampering.

FB-6 — App-only specials iOS 0.5d Android 0.5d

The channel exists: View/Home/HomeView.swift:29 renders Firestore-driven event banners (EventBannerCard, EventPosterView), Android mirrors it in ui/home/EventBannerCard.kt. The gap is merchandising, not plumbing.

  • Use the existing eyebrow field for an "App exclusive" label and give it a distinct badge style so app-only offers read differently from general events.
  • Pin app-only events to the front of the banner row.

Skipped: a separate promotions service, deep-link targets per banner, and a dedicated specials tab. Add when there are more offers than the banner row can hold.

Verify — a Firestore event flagged app-only shows the badge and sorts first; existing events render exactly as before.

FB-7 — Performance monitoring iOS 0.5d Android 0.5d

Firebase is already a dependency (Podfile: Core, Messaging, Firestore, Storage), so this is a pod plus initialisation, not a new vendor.

  • Add Firebase Crashlytics and Performance Monitoring; upload dSYMs from the release build phase.
  • Instrument the four traces that matter: app start, menu load, order preview, order submit.
  • Add the privacy-manifest and store data-disclosure entries the new SDKs require — the same disclosure step that caused the 2026-08-18 rejection.

Skipped: a third-party APM, custom metric dashboards, and alerting rules. Firebase's own console covers "regularly test and optimize"; revisit if it proves blind to something real.

Verify — a forced test crash appears in Crashlytics with symbols; the four traces report in the console; release build size and cold-start time measured before and after.

FB-8 — Ingredient and allergen transparency iOS 0.5d Android 0.5d content: blocking

Product attributes already decode (View/Model/ProductModel.swift:73) and ItemDetailsView already reads attributes by name. So the app change is to render Ingredients and Allergens attributes as their own labelled section in View/Product/ProductDetailsCard.swift, below the description at line 118.

  • Store side: add the two global attributes in WooCommerce and populate per dish. No schema change, no new endpoint, no app release needed to update the text afterwards.
  • Absent attributes render nothing, so partial content rollout is safe.

Skipped: structured nutrition tables, dietary filter chips, and an allergen preference profile. Add when the catalog actually carries complete data for every dish.

Flag: allergen text is a food-safety claim. It needs kitchen sign-off and a "may contain traces" disclaimer, decided by Trinhs, not by us.

Verify — a dish with both attributes shows both sections; a dish with neither looks unchanged; long ingredient lists wrap and stay scrollable.

FB-9 — Accessibility iOS 4d Android 2.5d

This is the most real of the nine and the least visible. The whole iOS target currently has 8 accessibility* usages across 3 files — effectively nothing. Icon-only buttons (favourite, cart, quantity steppers, the raised centre Orders button) are unlabelled, so VoiceOver announces them as bare buttons.

  • Scope the pass to the money path only: Home → Menu → item detail with add-ons → cart → pickup slot → checkout → order received.
  • Labels and hints on every icon-only control; images get labels or are hidden from VoiceOver as decorative (the report's "alternative text for images").
  • Dynamic Type: verify the flow at the largest accessibility text size and fix clipped fixed heights — LoginView's 55pt fields and the tab bar are known offenders.
  • Contrast check on the gradient buttons and grey secondary text against WCAG AA.
  • Respect Reduce Motion for the banner carousel and Lottie loaders.

Skipped: voice commands (the report asks for them; on iOS this is Voice Control and Siri's job, not ours — correct accessibility labels are what make Voice Control work, so labelling delivers the request), plus full VoiceOver coverage of the orphan screens (SettingView, ItemDetailsView, SaleView, DiscountView, RewardsCenterView) that nothing navigates to.

Verify — the full order flow completed end to end with VoiceOver on and the screen curtain enabled, plus at largest Dynamic Type with no clipped or unreachable controls. This is a manual QA gate, signed off before submission.

FB-10 — Store rating prompt iOS 0.25d Android 0.5d

Not from the report — requested alongside FB-5. Both stores expose a native in-app rating sheet, so nobody has to leave the app to rate it.

  • iOS: @Environment(\.requestReview) in OrderReceivedView, 1.5s after the receipt appears. No dependency. StoreKit decides whether the sheet shows and caps it at three times a year, so there is no counter in the app.
  • Android: Play In-App Review (com.google.android.play:review-ktx) from OrderReceivedScreen at the same moment. Play quotas it the same way and reports nothing about the outcome.
  • Both: a "Rate the App" row in Profile that opens the listing directly, because the native prompt is quota-limited and often silently skipped.

Policy constraint: Play forbids asking about sentiment before launching the review flow, so FB-5's feedback wheel and this prompt stay separate — no "are you happy?" gate in front of either, and they are not chained in one session.

Skipped: counting orders before prompting, and any custom rating UI. The store APIs already throttle, and a custom prompt cannot write a real review.

Blocked on: the numeric App Store id for the iOS Profile row (APP_STORE_ID in App/Config.swift); the row hides itself while it is empty. Testing the prompts needs a Play internal-testing track and a TestFlight or App Store build — neither fires on a simulator or a debug install.

FB-1 and FB-4 — Store listing and screenshots non-engineering

Runs in parallel with Sprint 1 and blocks nothing in code. The report only assessed Play, but the App Store listing has the same thin copy, so do both at once.

  • Rewrite the long description around real features, bulleted, with Vietnamese-cuisine and pickup-ordering keywords. APP_DESCRIPTION in App/Config.swift:28 is the in-app about text — update it to match so the two do not contradict.
  • New feature-led screenshot set: 6 frames per store, from real app captures, sized for current device classes (iPhone 6.9" and 6.5", plus Play phone and 7"/10" tablet).
  • Constrained by D3: only features that exist.
Verify — both listings updated and live; screenshots pass store size validation; nothing in the copy names a feature the build lacks.

5. Android parity notes (weeks 6–8)

The KMP module is 120 Kotlin files with screens mirroring iOS one-to-one (ui/auth/LoginScreen.kt, ui/home/HomeScreen.kt, ui/product/ProductDetailScreen.kt, ui/profile/), plus shared AuthViewModel, AuthService and AuthTokenStore. Parity work is therefore mostly Compose UI, not architecture.

  • Anything that lands in shared/commonMain during the iOS sprints — new response models for the social-auth and feedback-link routes — is written once and reused, so keep those additions in commonMain rather than in the iOS-only Swift models.
  • FB-3 on Android is Credential Manager with Google ID, hitting the same /auth/social route. No Apple sign-in.
  • FB-9 on Android is contentDescription on icon buttons, touch-target sizes, and a TalkBack pass over the same order flow. Decorative images get null.
  • Build and verify on Android only; the KMP iOS target stays out of scope, matching the existing project constraint.
